# 三个 bug 的复盘

面试里比「我做了什么」更好用的，是「我发现并修了什么」。这三件事都有现象、根因、修法和数据。

## 1. 漂移提示被覆盖：两个来源写同一个字段

**现象**：模型改了文件但没更新任务清单时，系统提示里偶尔看不到「漂移警告」；把同一会话 replay 出来，警告时有时无。

**根因**：进度尾部（`progress_tail`）和漂移提示（`drift_notice`）都拼进 `cfg.task_brief`，后写的覆盖先写的。两者来源不同（文件系统 vs 事件），生命周期也不同，却共用了一个槽位。

**修法**：拆成一个纯函数 `_brief(progress, drift_notice)`，明确「有漂移就追加，而不是替换」，并加测试钉住「只有 progress」「只有 drift」「两者都有」三种组合。

**为什么值得讲**：典型的「状态被两处写」缺陷；修法不是打补丁，而是把合并语义显式化。

## 2. 压缩风暴：小窗口下每轮都付一次摘要钱

**现象**：4k 窗口跑长任务，一次会话触发了 11 次 `model.request {kind: "compact"}`，成本是基线的 5 倍，tokens 反而只降了一点。

**根因**：压缩判定只看「是否超预算」。压缩完成后历史仍然偏大，下一轮又超，于是每轮都压；每次压缩都要一次完整的模型调用。

**修法**：`run.compact_cooldown`（默认 2 个 turn）——两次自动压缩之间至少隔一轮，把「压缩频率」和「压缩阈值」解耦。

**数据**：同任务压缩调用 11 → 7；成本从 5× 基线降到约 1.8×。代价是极端窗口下可能晚一轮压缩，用溢出重试兜底。

**为什么值得讲**：优化不能只看 token，必须看「为了省 token 花了多少钱」。

## 3. 干完不交卷：模型不调用 `finish`

**现象**：仓库级任务 `repo-sessions-filter` 连续两次跑到 45 步上限，0 次 `finish`。把它的工作区单独跑验收，**隐藏测试全过**——实现是对的，行为是错的。

**根因**：`finish` 需要模型主动调用；模型在「测试绿了」之后仍继续探索（读更多文件、写临时脚本、再验证）。先加的「步数到 75% 时发一条 user 消息」无效，因为提示离工具结果太远，模型注意力还在上一条输出上。

**修法**：把提示放进模型一定会读的位置——**最后一次编辑后的第一次成功 `bash`**，在其工具结果末尾追加一句「验证已过，若完成请现在调用 finish」。同时系统提示增加一条「验证通过后同一轮 finish」。

**数据**：同一任务从 45 步 max_steps（519k tokens）变成 **10 步通过**（50k tokens）；大任务 `edit_lines` 在 60 步预算下 54 步通过。

**为什么值得讲**：这是评测驱动的修复——先有失败分类数据，才定位到「提示位置」而不是「提示内容」；修复只有十几行，效果是 4.5 倍步数差。

## 共性

三个 bug 都不是「算法错了」，而是**状态边界、成本边界、交互边界**的问题。这个项目的价值也主要不在模型，而在把这些边界用代码和测试固定下来。
